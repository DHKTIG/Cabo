# CABO 完整游戏程序 — 开发准备清单

> 面向 Go 实现。整理日期：2026-10-29
> 配套文档：`CABO-玩法详解.md`

---

## 0. 一句话结论

做这个游戏，**代码只占三成工作量**。剩下七成是：

1. **把口头规则变成无歧义的规格** —— CABO 有大量家庭变体，模糊点会在实现阶段集中爆发，返工成本极高。
2. **定死信息可见性模型** —— 卡牌游戏的本质是"谁知道什么"，这块设计错了要推倒重来。
3. **决定实时性要求** —— 纯回合制，还是带抢牌（Burn）的实时制？这一个决定直接决定要不要引入并发。

下面的清单按"现在就该做"到"后期再说"排序。

## 1. 第一步：规则规格化（占总准备量约 40%）

### 1.1 必须现在拍板的 17 个歧义点

这些点不同版本说法不一，**必须现在选定并写进规格**，否则写代码时每个都会变成一次临时决策，最后互相矛盾。

| # | 歧义点 | 常见选项 | 建议 |
|---|---|---|---|
| 1 | 开局看几张、看哪几张 | 固定左右各一 / 自选 2 张 / 看全部 4 张 | **自选 2 张**，策略空间更大 |
| 2 | 看完能否调整手牌顺序 | 可以 / 不可以 | **不可以**，否则记忆无意义 |
| 3 | 能力牌数字映射 | 7-8 看自己 / 9-10 看对手 / J-Q 交换 | **采用此映射**（官方 App 版，最对称） |
| 4 | 从弃牌堆拿的牌是否保持明牌 | 保持明牌 / 变回暗牌 | **保持明牌**（第二版），逻辑自洽 |
| 5 | 「1 换多」的判定基准 | 换出的牌**彼此**同点 / 与被拿走的牌同点 | **彼此同点**，这是原版设计 |
| 6 | 1 换多最多换几张 | 无上限 / 最多 3 张 / 最多 4 张 | **最多 3 张**，惩罚梯度才合理 |
| 7 | 翻错惩罚 | 收下牌 / 收牌+罚抽 / 分级 | **分级**：翻错收牌；涉及 ≥3 张再罚抽 1 张 |
| 8 | 从弃牌堆拿牌能否发动能力 | 可以 / 不可以 | **不可以**，只有摸牌堆才触发 |
| 9 | 喊 CABO 后其他人 | 各行动一次 / 各行动一轮 | **各行动一次** |
| 10 | 喊 CABO 后自己的牌能否再被换 | 锁死 / 仍可被 SWAP | **锁死**，否则"喊了也能被翻盘"体验差 |
| 11 | 平局判定 | 喊者胜 / 重开一轮 / 并列 | **喊者胜**（先喊者优先） |
| 12 | 牌堆摸空 | 立即结束计分 / 洗弃牌堆续上 | **洗弃牌堆续上**（实装改的：留一张明牌，两堆都空才结算） |
| 13 | 100 分重置 | 恰好 100 / ≥100 / 无限次 | **恰好 100，限一次** |
| 14 | 超过 100 分 | 立即结束 / 打满整轮 | **打满整轮再结算**，避免中途打断 |
| 15 | 2 人局特殊规则 | 与 4 人相同 / 特殊（如各 5 张） | **相同**，先不做特殊平衡 |
| 16 | 神风特攻队 QQKK | 启用 / 不启用 | 建议**做成可选开关**，默认关 |
| 17 | Burn 抢牌 | 启用 / 不启用 | **先不启用**，第二阶段再加 |

> 拍板方式：拉个表，每项勾一个，5 分钟搞定，比写代码时纠结 5 小时强。

### 1.2 输出物：一页纸的规则规格

规格要写成**状态转移表**的形式，而不是散文。例如：

```
状态: TurnWaiting
  输入: DrawFromDeck  → 状态 TurnHasDrawn，摸牌堆 -1，记录 pendingCard
  输入: TakeDiscard   → 状态 TurnClaiming，记录 pendingCard = 弃牌堆顶
  输入: CallCabo      → 状态 CaboFinalRound，caller = 当前玩家
  其他输入            → 拒绝，返回 ErrNotYourTurn / ErrInvalidAction

状态: TurnHasDrawn
  输入: DiscardPending      → 弃牌堆 +1，回到 TurnWaiting，下家
  输入: SwapInto(idx)       → 手牌[idx] 进弃牌堆，pendingCard 入手牌，回到 TurnWaiting
  输入: UsePower(power)     → 仅当 pendingCard 是能力牌；执行后 pendingCard 进弃牌堆

状态: TurnClaiming            // 从弃牌堆拿牌
  输入: DeclareSwap(indices) → 校验：所有 indices 的牌彼此同点
    校验通过 → 弃牌堆 +len(indices)，pendingCard 入手牌
    校验失败 → 惩罚流程（见规格 3.2）
```

**这一页纸就是整个项目的地基。** 后面所有测试用例都从这里派生。

## 2. 信息可见性模型（最容易被低估）

### 2.1 三种信息层级

| 层级 | 内容 | 谁能看到 |
|---|---|---|
| 公开信息 | 弃牌堆、牌堆剩余数、各家手牌数量、各家累计分数、当前轮到谁 | 所有人 |
| 私有信息 | 自己的 4 张牌、自己开局看到的那 2 张 | 仅自己 |
| 隐藏信息 | 别人的暗牌、牌堆顺序 | 无人（服务端才知道） |

**必须做到：任何发给客户端的报文，都只包含该玩家有权看到的信息。** 这是硬约束，不是优化项。

### 2.2 「记忆」要不要由系统托管？

这是 CABO 独有的设计难题，因为它是一款**记忆游戏**。三种方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **硬核** | UI 只显示牌背，玩家自己记 | 忠于原版，紧张感强 | 线上体验差，玩家会截图作弊 |
| **半辅助**（推荐） | UI 显示"你已知的牌"，但该牌一旦被换走/被 SWAP 就**立刻清除标记** | 降低门槛，仍保留记忆压力 | 需要维护"已知集合"并正确失效 |
| **全辅助** | 永久记录所有曾见过的牌 | 最友好 | 变成纯概率游戏，失去灵魂 |

**推荐半辅助**，但要实现一个 `KnownSet` 机制：

```go
// 玩家 i 对手牌 j 的认知状态
type Knowledge struct {
    Known   bool  // 是否已知
    Value   Card  // 已知的值
    Stale   bool  // 已失效（位置被换过但玩家没察觉）
}
```

关键规则：**当一张牌离开玩家视野（被 SWAP 走、被对手换走）时，必须把对应的 Known 置为 false**。这一步很容易漏，漏了就是"外挂级"信息泄漏。

### 2.3 视角裁剪

```go
func (s State) ViewFor(pid int) PlayerView {
    // 自己的牌：给全值
    // 别人的牌：只给数量 + 该玩家自己 Known 的那些
    // 牌堆：只给 len(Deck)
}
```

## 3. 数据模型设计

### 3.1 核心类型

```go
type Card struct {
    Rank  int    // 0-13
    Suit  Suit   // 用于区分方块K和Joker
    ID    int    // 唯一标识，用于追踪"这张牌去哪了"
}

type Action interface{ isAction() }  // 密封接口，防止非法动作

type DrawFromDeck struct{}
type TakeDiscard  struct{}
type DiscardPending struct{}
type SwapInto     struct{ Index int }
type UsePower     struct{ Power Power }
type ClaimSwap    struct{ Indices []int }
type CallCabo     struct{}

type Event interface{ isEvent() }    // 用于前端动画和回放

type CardDrawn   struct{ Player int }
type CardSwapped struct{ Player, Index int }
type PowerUsed   struct{ Player int; Power Power }
type CaboCalled  struct{ Player int }
type RoundScored struct{ Scores []int }
```

### 3.2 为什么要有 `Card.ID`

每张牌给唯一 ID，好处：
- 调试时能追"这张 K 从牌堆到 A 手上到弃牌堆"的完整轨迹
- 回放系统不需要存牌面，存 ID 序列即可
- 测试可以断言"总牌数守恒"

### 3.3 事件溯源 vs 快照

| 方案 | 做法 | 适用 |
|---|---|---|
| 快照 | 每次动作后存完整 State | 简单，够用 |
| 事件溯源 | 存 seed + 动作序列，重放还原 | 回放、审计、AI 训练 |

**建议：两者都做。** 快照用于断线重连（快），事件流用于回放（省空间、可分析）。

## 4. 技术选型（Go 侧）

| 需求 | 候选 | 建议 |
|---|---|---|
| Go 版本 | 已装 1.27.1 | 直接用，`log/slog`、增强版 `net/http` 路由都现成 |
| HTTP 路由 | 标准库 `net/http` | **够用**，1.22+ 的 `mux.HandleFunc("GET /api/x")` 已经很顺手 |
| WebSocket | `gorilla/websocket` / `coder/websocket`(原 nhooyr) | 后者更现代，API 更干净 |
| 前端 | 原生 HTML/CSS/JS + `go:embed` | **推荐**，单二进制部署，无需 node 工具链 |
| 前端框架 | Svelte / Vue | 只在动画复杂时才需要 |
| 存储 | JSON 文件 / `modernc.org/sqlite`（纯 Go，无需 CGO） | 先 JSON，有排行榜再上 SQLite |
| 日志 | `log/slog` | 标准库，结构化输出 |
| 测试 | `testing` + 表驱动 + `testing/fuzz` | 规则引擎非常适合表驱动 |
| 配置 | `encoding/json` 或环境变量 | 规则变体用配置结构体承载 |

**核心原则：能不加依赖就不加。** 这个游戏的规模，标准库 + 一个 WebSocket 库就够。

## 6. 五个真正的技术难点

### 6.1 隐藏信息泄漏
最容易犯的错：`json.Marshal(state)` 直接下发。必须走 `ViewFor(pid)`。
**自查方法**：写一个测试，断言序列化后的报文里不包含任何未公开的牌面。

### 6.2 抢牌并发（如果做 Burn）
多个玩家 5 秒内抢同一个动作。需要一个仲裁循环：

```go
select {
case claim := <-burnCh:
    if valid(claim) { apply(claim) }
case <-time.After(5 * time.Second):
    // 无人抢，继续
}
```
注意：**必须做幂等和超时**，否则玩家疯狂点击会把 goroutine 打爆。

### 6.3 断线重连
玩家刷新页面后要恢复现场。方案：用 token 认人，重连时下发 `ViewFor(pid)` 快照 + 当前阶段。**关键是把"已知牌"也一起下发**，否则玩家重连后记忆全丢。

### 6.4 计时器泄漏
每个回合一个 `time.Timer`，玩家提前行动时必须 `timer.Stop()`，否则几千局后内存里全是僵尸 timer。这是 Go 写游戏最常见的坑。

### 6.5 随机与回放
不要用全局 `math/rand`。用注入的 `*rand.Rand`（或 Go 1.22+ 的 `math/rand/v2`），种子存进对局记录。这样任何一局都能精确重放。

## 7. 素材与体验准备

### 7.1 卡牌视觉
- 数字牌 0–13，加特殊牌（方块 K、Joker）
- **不必找美术**：用 CSS + SVG 画纯色卡面就很好看，CABO 本身是极简风格
- 关键信息优先级：数字 > 能力图标 > 花色
- 能力牌要能一眼看出"这是 7/8 还是 9/10"

### 7.2 动画清单（按优先级）
1. 发牌（4 张依次落位）
2. 翻牌（自己看牌时）
3. 换牌（牌从手牌飞向弃牌堆）
4. SWAP（两张牌位置对调，带弧线）
5. CABO 揭示（所有牌同时翻开，最高分闪烁）
6. 计分（数字滚动累加）

**前三个必须做，后三个是加分项。**

### 7.3 音效清单
翻牌、换牌、错误提示、CABO 喊声、胜利。用免费素材库即可，或先留空接口。

### 7.4 布局适配
- 桌面端：对手在上方环绕，自己手牌在下方
- 移动端：对手横排顶部，手牌底部大卡片
- **先做桌面端**，移动端第二阶段

## 8. 测试准备

### 8.1 必须覆盖的规则用例（约 25 个）

按优先级：

**基础流程**
1. 正常发牌，每人 4 张，牌堆剩余正确
2. 摸牌后弃掉，回合切换正确
3. 摸牌后换入，旧牌进弃牌堆
4. 从弃牌堆拿牌，1 换 1

**能力牌**
5. 摸到 7 弃掉，触发 PEEK，只能看自己
6. 摸到 9 弃掉，触发 SPY，能看对手
7. 摸到 J 弃掉，触发 SWAP，交换两张牌
8. 摸到 K，无能力，不能触发
9. 从弃牌堆拿到 7，**不能**触发能力

**1 换多与惩罚**
10. 手上两张 3，弃牌堆顶 2，成功 1 换 2
11. 声明 1 换 2 但翻错 → 收下弃牌堆顶牌
12. 声明 1 换 3 且翻错 → 收牌 + 罚抽 1 张
13. 换出的牌数量超过上限 → 拒绝

**CABO 与计分**
14. 喊 CABO 后每人各行动一次
15. 喊 CABO 期间不能再喊
16. 喊者最低 → 0 分，其他人按点数
17. 喊者不最低 → 点数 + 10
18. 平局 → 喊者胜
19. 牌堆摸空 → 洗弃牌堆继续（留一张明牌）；两堆都空 → 结束计分
20. 累计 >100 → 整轮结束，最低分胜
21. 恰好 100 → 可重置为 50，且只能用一次

**不变量（属性测试）**
22. 任意时刻：牌堆 + 弃牌堆 + 所有手牌 = 总牌数（守恒）
23. 任意时刻：无人手牌超过 6 张（4 + 最多 2 张惩罚）
24. 任意时刻：分数非负
25. 随机模拟 10000 局，无 panic、无死循环、必定终止

> 第 22 条（牌数守恒）是最有价值的测试，一个断言能抓住绝大多数状态管理 bug。

### 8.2 测试组织方式

```go
func TestApply(t *testing.T) {
    cases := []struct{
        name    string
        setup   func() State
        action  Action
        wantErr error
        check   func(t *testing.T, s State)
    }{ ... }
}
```

表驱动 + `testdata/*.json` 存回放用例。

## 10. 里程碑与验收标准

| 阶段 | 目标 | 验收标准 | 预估 |
|---|---|---|---|
| **M0** | 规则规格文档 | 17 个歧义点全部拍板，状态转移表写完 | 半天 |

## 11. 现在就能做的三件事

1. **花 30 分钟把第 1.1 节的 17 个歧义点勾完** —— 这是唯一阻塞项，不做完不要动代码。
2. **画一张桌面草图**（纸上或 Figma 都行）—— 决定手牌横排还是 2×2、对手放哪、弃牌堆放哪。这决定前端 DOM 结构。
3. **想清楚一个问题**：你是想做一个"自己和朋友玩的工具"，还是"给别人玩的在线游戏"？
   - 前者：M3 就够了，不用 M5。
   - 后者：M5 的工作量是 M1–M3 的总和，要有心理准备。

## 附：Go 实现的技术风险自查表

| 风险 | 检查方式 |
|---|---|
| 隐藏信息泄漏 | 断言序列化报文不含未公开牌面 |
| 状态不一致 | 牌数守恒断言 |

| 并发写冲突 | `go test -race` |
| 死循环 | 随机模拟加最大步数上限 |
